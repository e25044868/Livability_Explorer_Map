# ADR-001：使用統一地點、JSON 特殊屬性與證據式關聯

## Status

Accepted

## Date

2026-08-01

## Context

政府資料中的停車場、公廁、AED、藥局、醫療院所與機車充電站有共同的名稱、地址、座標與來源資訊，但也有車位數、AED 地點描述、醫療科別等不同欄位。同一實體可能跨資料集出現，且「停車場有充電」可能代表官方明確提供、地址相同或僅在附近，三者不能混為一談。

系統還需支援未來便利商店服務，不應把 schema 寫死為六種政府設施。

## Decision

1. 所有設施共用 `places`，只放穩定的共同欄位。
2. 類別特有欄位放入有版本與驗證規則的 `properties` JSONB。
3. 跨資料集資訊使用 `place_relations`，保留 `relation_type`、`evidence_method`、距離、信心值與證據。
4. 公開 UI 必須依證據方法使用不同文字：
   - 官方明確資料：場內設有。
   - 地址匹配：同址有。
   - 空間距離：N 公尺內有。
5. 相同名稱或座標只產生重複候選，不直接刪除。
6. 目前充電類別命名為 `motorcycle_charging`，直到取得可信汽車充電資料後再新增獨立類別。

## Alternatives Considered

### 每個類別一張資料表

- 優點：欄位型別明確。
- 缺點：空間查詢、多類別摘要與未來新增類別需要大量 UNION 與 migration。
- 不採用：產品核心是跨類別生活圈分析。

### 所有欄位都放進 places

- 優點：單表直觀。
- 缺點：大量稀疏欄位，政府來源變動會頻繁改 schema，也會把內部欄位意外暴露給 API。
- 不採用：共同欄位與特殊欄位的生命週期不同。

### 只用距離推定並顯示「有充電」

- 優點：實作快速。
- 缺點：會把附近站點誤導成場內服務，無法追溯判斷依據。
- 不採用：違反資料透明與不誤導原則。

## Consequences

- 新類別通常只需新增類別值、來源設定與 properties validator。
- API 必須使用各類別公開 allowlist，不能原樣回傳所有 JSONB。
- 關聯計算可重跑且可由人工證據覆蓋，但需保存演算法版本與產生時間。
- 前端必須顯示關聯證據標籤，不能只顯示單一布林值。
